# Academic Source Coverage Research

Research date: 2026-09-05

## Product decision update (2026-09-06)

The original least-privilege recommendation below was implemented and live-tested, but Chrome closes an extension action popup while showing a permission prompt. In practice, the per-origin design created an obscure two-step workflow: users had to open Papername, grant access, reopen it, and invoke the action again. That contradicts the product's core promise of automatic naming, and a static origin list cannot cover university proxies or institution-specific repositories.

The MVP therefore accepts the higher-trust install posture and now requires `http://*/*` and `https://*/*` access. Chrome displays a broad website-access warning; the beta listing and privacy disclosure must explain that Papername uses page access locally and solely to detect academic citation metadata. Users can narrow or disable access through Chrome's built-in Site access controls. ResearchGate remains explicitly excluded. On generic sites the content script observes only document-head metadata, while curated academic sources may require full-document observation.

Google Scholar is covered by a local click adapter: when the user activates a side link labeled `[PDF]`, Papername captures the visible title, author line, year, and exact selected URL. This can identify many university-proxy downloads without automated Scholar queries or backend scraping. Search snippets are not treated as abstracts, and session-bound or opaque proxy redirects remain an honest limitation.

## Original recommendation and evidence

The initial recommendation was a three-level resolver with narrower permissions:

1. Continue automatic support for a curated set of well-tested publisher origins.
2. On any other page, let the user invoke Papername once. Chrome's `activeTab` permission gives temporary access to the active tab after that explicit gesture and causes no install warning; `chrome.scripting` can then run the same generic metadata extractor on the page ([Chrome `activeTab`](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting)).
3. Offer “Always enable on this site” as an optional, per-origin grant. Chrome supports hosts discovered at runtime by declaring `https://*/*` and `http://*/*` under `optional_host_permissions`, then requesting only the current origin through `chrome.permissions` ([Chrome permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions), [permission declaration guidance](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)).

This avoids the high-trust `Read and change all your data on all websites` install posture. It also deals with the central repository problem: EPrints, DSpace, and Digital Commons run on thousands of institution-specific domains, so no static domain list can cover them.

For automatic mode, fingerprint the page's metadata and URL shape rather than guessing from a hostname. Prefer, in order: `citation_*`/Highwire metadata, Dublin Core, `ScholarlyArticle` JSON-LD, platform-specific metadata, then narrow URL-to-landing-page recovery. Do not add general backend crawling.

## Direct-PDF recovery and its limits

“Almost universal” needs a layered recovery path, because a bare PDF response often contains no trustworthy bibliographic context:

1. Match the download URL against `citation_pdf_url`, Dublin Core identifiers, JSON-LD content URLs, and platform-specific PDF fields captured from the landing page.
2. Use Chrome's download referrer where present, but do not trust the last active paper globally.
3. Apply narrow same-origin route transforms only where the URL deterministically identifies the record: arXiv PDF to abstract page, EPrints file to record root, and DSpace bitstream to Handle/item/API record. Do not derive a Digital Commons landing page from `viewcontent.cgi`: its `article` query value is an internal upload ID and can differ from the public record number. Likewise, do not fetch SSRN delivery-to-record routes; use metadata already captured in the article tab.
4. If an unknown direct PDF is the active tab, present “Name this PDF” as an explicit one-shot action. Identifier lookup from a DOI/arXiv ID/PMID found in the URL is inexpensive and high-confidence.
5. Treat bundled local first-page PDF extraction as a later fallback. It adds a PDF parser to the extension, increases package size and CPU/memory use, may fail on scans or unusual encodings, and still requires a confidence UI when title/author inference is ambiguous. It should remain local and opt-in; sending the PDF to a server would materially change Papername's privacy promise and operating cost.

Even with these layers, universality is impossible for scanned PDFs, encrypted files, blob/data URLs mediated by another extension, session-bound downloads, pages without bibliographic metadata, or files whose landing page is not recoverable. The correct behavior remains an unchanged filename plus an actionable reason, never a guessed paper name.

## Cost, usability, and policy caveats

- Generic local metadata extraction and platform route matching have no marginal API or LLM cost. OSF and institution-hosted repository APIs can be queried only when needed and cached per navigation.
- Crossref DOI metadata is an effective shared fallback for Nature, SSRN, and repository records, but not every repository deposit has a DOI and Crossref metadata can omit abstracts. It should enrich identity, not override stronger same-page data.
- Broad required host permissions create a significant install warning and trust burden. The MVP accepts that cost for zero-click coverage, requires prominent disclosure, keeps extraction local, and points users to Chrome's Site access controls ([Chrome permission declaration guidance](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)).
- A required-site-access update may pause the installed extension until the user accepts the new permission. Beta update instructions must call this out explicitly.
- Publisher and platform policies are not uniform. Keep metadata work local to the user's active page, never defeat authentication/paywalls, never automate ResearchGate, and avoid backend scraping of SSRN or publisher pages.
- Platform recognition needs fixture tests plus a small live smoke matrix. Institutional administrators routinely customize templates, field names, base paths, authentication, and redirects even when they use the same repository software.

## Suggested delivery order

1. Ship automatic generic extraction on HTTP(S) article pages with explicit install/listing disclosure and Chrome Site access instructions.
2. Add curated Nature support and metadata aliases for `eprints.*` and `bepress_citation_*`.
3. Add OSF's GUID/API adapter and SSRN's in-tab `abstract_id`/delivery matcher.
4. Add narrow EPrints and DSpace direct-PDF recovery with representative fixtures. Keep Digital Commons matching anchored to `bepress_citation_pdf_url` captured from its landing page.
5. Explicitly mark ResearchGate as unsupported for policy reasons.
6. Measure `permission_needed`, `missing_metadata`, `unmatched_download`, and platform-specific success only as existing aggregate outcome counters; do not send domains, URLs, titles, authors, or filenames.
